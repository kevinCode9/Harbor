### 3.2 Visitor entry, identity and document control

**Purpose:** entry and refresh have predictable outcomes, and competing documents cannot act as independent controllers of the same session.

- Distinguish fresh admission, session continuity, document identity and current control. Cookie is not identity; historical receipts do not restore obsolete current authority.
- **Admission door:** new admission only through bare GET / while the Site is ON. An inner URL without valid resume material goes offline; it is not an alternate fresh-admission door. Reference map 312 records this contract; it is not a new implementation claim.
- **Authorized refresh/reload:** preserves the authorized visitor session and reconstructs applicable persisted state. It is not a new visitor. It is not still-open reconnection. Refresh does not delete already-persisted backend data. Reconnect and refresh-before-reconnection: §3.3.
- A later correction allows native duplicate copies to share a session. Only one controlling document is allowed; copies must reconcile before acting.
- Current Page means an accepted visitor-confirmed landing, not merely an Admin click or intended destination.
- Admission, grant, visible display and landing confirmation are distinct milestones. A successful HTTP response alone does not prove all four.

**Source:** Archive 1621 and 1829–1834; Reference map 311–315, 466–469; supplied later admission/document reports. **Reconciliation:** do not copy the archive's blanket new-tab rule without the duplicate-copy correction.

### 3.3 Presence, absence and session ending

**Purpose:** Admin can distinguish a currently available visitor from an absent one without confusing availability, authority or data retention.

- Keep Presence, session identity and document control separate. Typing recency, IP address and another session's activity are not Presence. Presence is not control. Do not silently choose controller-only or every-copy Presence.
- **Presence** means whether the visitor is viewing the page. Viewing counts as present/active even without typing or clicking. Presence is not connected/disconnected status. A live connection does not prove present. A dropped connection does not prove absent.
- After the visitor stops viewing, the Admin Presence **indicator** changes to absent after approximately 2 seconds. That delay is a display rule only. Do not apply it to the 30-minute continuous-absence clock unless a later named requirement says so.
- Keep Presence separate from document authority, the 30-minute continuous-absence deadline, End Session and Site OFF. Those remain different conditions with different outcomes.
- Browser signals and implementation mechanisms remain unselected. Open item: §5.1.
- Duplicate copies may share one session (§3.2). The **actively used** copy takes control. One controller. One Admin row/target. The previous controller loses authority. Catch-up before acting. **Engineering unresolved (not a product reopen):** browser signals, transfer races, ambiguous simultaneous-use. Native Duplicate UI proof remains unverified. Open item: §5.1.
- Admin disconnection must not end the visitor session.
- **End Session:** send the visitor to that session’s separate individual-exit destination. Remove the visitor from the Admin list. Retain invalidation/history until applicable retention expiry, without restarting clocks. Compatible with a retained invalidation/tombstone. Not deletion and not revival. No normal Ended/history list entry is requested. Admin-list removal and retained history do not replace the individual-exit destination.
- **Visitor absence:** 30 minutes of continuous **not viewing** → offline. Not Admin idle. Not the ~2s Presence indicator. Not seven-day retention. Signal contract: checkpoint **7**. Enforcement: checkpoint **11** after **10** (same viewing signal; recommended order). Do not implement an early throwaway timer.
- Existing ended or revoked sessions must not regain authority simply by reconnecting.
- **Still-open page reconnect:** typing stays enabled locally. If the page stays open, its latest local values catch up after valid reconnection. If the visitor refreshes before reconnection, not-yet-sent offline edits are not required to survive. Refresh does not delete already-persisted backend data. This does not select a recovery mechanism or establish browser-closure recovery. Example: if the backend last received `ban` and the visitor finishes `banana` while disconnected and the page stays open, reconnection sends that latest local value. This supersedes pause-editing / offline-editing-not-selected. It does not prove current implementation. Intermediate offline-history and offline submissions/navigation remain open. Do not revive expired, ended or revoked authority, or let a stale document overwrite newer authorized state.

**Source:** Archive 1645–1656; Reference map 313–316. Actively used copy / Native Duplicate UI: see bullets above and §5.1.

**Recovery terms:** authorized refresh/reload: §3.2 and §3.4. Still-open catch-up and refresh-before-reconnection: this section (settled). Multiple Admins remain subject to authorization, stale-operation handling and correctness. That does not select a winner or add a conflict UI.

No form-resubmission prompt, command replay, or dependence on the Admin remaining connected. Archive 1008. This does not prove current implementation. Refresh-before-reconnection of not-yet-sent offline edits: §3.3.

### 3.5 Admin cards and Preview

**Purpose:** an Admin can inspect a page presentation without affecting a real visitor.

- Preview and Send are different operations.

- Unsent card drafts are private to each Admin. Selecting visitor B closes A’s card menu and discards A’s unsent values. Do not transfer them to B or restore them on returning to A. Visitor state and Activity are not reset.
- Admin refresh discards unsent card values. Logging back in does not restore them. Saved visitor data and Activity remain unaffected. This does not select a storage mechanism or prove implementation. Storage mechanism remains unselected. Open item: §5.1.
- A visitor's confirmed Current Page changing does not by itself reset/rebuild the Admin-owned right menu or cards. The explicit selected-visitor switch above is a different trigger.
- Preview must not create visitor sessions, update Current Page, generate visitor Activity or send real navigation.
- **Preview target (recorded, not build-now):** a centered in-Admin surface, not iframe-based. Reuse visitor-page presentation. Keep identity, state and side effects separate. Preview interaction is temporary and does not require durable visitor writes. A real visitor route plus a query flag is not the final isolation boundary. ### 3.8 Admin access and security lifecycle

**Purpose:** authorized access to this website remains revocable, document-specific and distinct from visitor identity.

- One central server-side authorization authority; no competing permanent access mechanisms.
- **Four distinct concepts:** Laravel framework sessions; Admin **document access identity** (grant); durable Admin **audit**; visitor UserSession product identity. Do not merge them because they share the word session. These are conceptual distinctions. They do **not** mandate separate tables. No additional session-index store is selected. Suitable use of existing storage is not prohibited.
- Distinguish operator setup authority from Site Admin access. **Sub-Admin is out of the product.** Access stays disabled (checkpoint **2** reports: HTTP 410 / `accessViaKey` 404). Leftover `sub_admin_accounts` retained per those reports; physical removal is checkpoint **14**. No target-product use is identified. Existing data disposition remains to be explicitly included in the authorized retirement scope, with recovery. Do not restore access.
- Every successful authentication creates a **separate Admin document access identity**. A new tab or browser authenticates. Refresh authenticates again. Refresh or disappearance is **not** explicit Logout. These identities use the **same current Site Admin key**. They must **not** inherit authorization or update each other’s last-seen through shared cookies.
- **Backend-only Admin information:** reported browser/device information; **successful login time**; viewing-based last seen; **explicit Logout time**. Do not expand this list from historical audit suggestions. Do not infer authorization to delete existing data. **Schedule:** login-time browser/device, successful login time, and explicit Logout time belong with checkpoint **2** access. Viewing-based last seen and one-hour not-viewing **enforcement** belong with checkpoint **10** (planned realtime after checkpoint **7** signal design). No temporary HTTP Presence.
- **Logged out** means an explicit Logout click only. Do not label refresh, tab closure, disconnection, expiry or revocation as explicit logout. Keep expiry/revocation **enforcement** separate from that label.
- **Keep separately** (not extra fields of the four-item list; not a required extra table): Send requested / confirmed / failed / unresolved; revocation status and time. There is **no scheduled Admin access expiry**. Durable **audit** (login success/failure and related access events) is the current audit owner; physical placement of the requested Admin information remains unresolved. Never record the raw reusable Site Admin key. Implementation evidence: §4.1 / §5.0.
- This website has one current Admin key generated/regenerated through operator-controlled setup/maintenance commands; no management screen requested. Durable storage holds the verifier only. There is **no scheduled key or grant clock**. Regeneration invalidates Admin access using the old generation. Visitor sessions continue unless a visitor lifecycle rule says otherwise. Column `sites.admin_key_expires_at` may remain; mint writes `null`; verify ignores it. New `admin_document_grants.expires_at` is `null`; live/prune ignore that column as an access deadline. Historical non-null grant dates are not a deadline.
- Leftover **MASTER-1** is leftover implementation, not this requirement, and is **not** checkpoint **2** login.

**Accepted access contract (product; sandbox APPLY recorded **§4.1**; not PASS):**
- Form Continue/Enter sends an explicit authentication **fetch POST** from the unprivileged login document. Typing/pasting does not submit.
- Success returns the document grant to **that** requesting document. Keep it in memory only. Start the authorized dashboard **explicitly, once**. Then `replaceState` to the **existing** clean dashboard URL with **no** secret in `history.state`.
- Key-bearing entry loads the unprivileged login bootstrap; capture the key in memory; clean that address **before** the same POST. Original entry-URL exposure is acknowledged. Do not invent new entry syntax.
- Refresh / new Admin document: no grant → login. No remembered login. That is **not** logged out.
- Every successful authentication opens the main sessions list with no restored selected session, detail or card. In-document selection continues normally. Reset navigation state only; this is not authority to delete visitor records or unrelated draft storage. Implementation and browser limits: **§4.1**.
- Logout (explicit click) revokes **this** document grant only and records **explicit logout time** for that session (`admin_access_events.type=logout` on that request). Login teardown / failed-start cleanup revokes the grant without that logout label. Login and explicit-logout audit IPs are that request’s `Request::ip()`.

- Mounting markup does not authorize. Protected requests need the live document grant and the applicable website/session/lifecycle checks. Authentication responses that contain grants must not be cached.

The dashboard may remain visible but unauthorized; returning must not silently restore access; refresh goes to login. Passive incoming updates do not keep unattended access alive; visitors continue independently. Do **not** treat missing reports as not viewing. Do **not** invent reporting intervals. **Implementation** with planned realtime after signal design (checkpoints **7** then **10**). Not a checkpoint-**2** scoped-access completion blocker. No temporary HTTP Presence. Interim 1800s interaction: **§4.1**.

Explicit Logout revokes that Admin document only. Key regeneration affects the Admin documents using that generation, without unintentionally ending visitor sessions.
